ADR 004: Flat entity model, narrative namespace, and entity-indexed history
Status: Superseded by ADR 006
Supersedes: ADR 002 §§1–6 and §8 (the ledger, its merge/retraction grammar, and the ROSTER rendering it fed) and the plain-text shape of `archive.Turn.Update`/`Events`. Leaves ADR 002 §7 (TIMELINE), §9 (pinned system message), §10 (recall counts as a round) and all of ADR 003 (locations, conservation, position ownership) unchanged.

Context
- Measured failure: inventory tracking broke down in play. Tracing it did not land on a wording problem the way ADR 003's dagger case did. It landed on identity: `placementKey(name, where)` (rules/location.go:141) builds an item's storage key out of *where it currently is*. Move the item and the key changes completely — nothing links what disappeared under the old key to what appears under the new one. Items are the one entity type in the engine with no identity independent of position, and a thing whose address is its only name cannot be tracked across the one action — moving — that a game does constantly.
- The block splits one entity's facts across three sections: ROSTER (`rules.World`, computed), LOCATIONS' `here:` line (also computed), and WORLD (the ledger, DM-authored). Nothing here was unsafe on its own — `engineOwned` already stripped known engine fields from ledger lines — but three sections joined by the reader is three places a fact about one thing can be written, and gives no single place to look a thing up.
- The ledger's guard works by name: a fixed denylist of fields (`wounds`, `coins`, `at`, ...) rejected on ingest. That stops a restatement of a *known* field. It does not stop the DM inventing an unlisted synonym — `where`, `current_room`, `physical_position` — that isn't on the list and, over enough turns, becomes the field the DM reads back as true. That is the same entropy ADR 002 was written to stop, one layer further out: not "the DM restates wounds," but "the DM invents a second word for position and starts trusting it."
- Recall (`archive.Lookup`) answers by substring match over prose and joined update text (`archive.Turn.Update`, `mentions()` in archive/archive.go:202-210). That is document retrieval — "does this text contain the word merchant" — even though every call that touches an entity already names it explicitly to make the call. The ID was sitting in the argument list the whole time; recall just wasn't indexing on it.

Decision
1. Every entity — Character, Item, Location, or a narrative-only construct with no engine fields at all (a rumor, a faction's standing) — gets a unique, engine-assigned, immutable ID and appears exactly once in one flat `entities:` map rendered to the DM each turn. No entity's rendering nests inside another's; a relationship between two entities is a reference by ID, not one entity's text containing the other's.
2. Items become entities with a stable ID for the first time. `AddItem`/`RemoveItem`/`find` (rules/location.go) stop keying storage by `placementKey(name, where)` and key by ID instead; name and spot become a lookup index onto that key, not the identity itself. `location` is an engine-owned attribute on the item, referencing another entity's ID, checked exactly as `move_item` already checks a destination exists. A partial stack move mints a new ID for the portion that moved; the original ID stays with whatever is left behind. Landing on an identical existing stack retires the absorbed ID rather than carrying two.
3. The kernel — what the engine validates on every entity regardless of type — stays deliberately small: a unique ID, a `type`, and every reference resolving to an ID that exists, checked across one global keyspace shared by engine entities and narrative-only entities alike (a rumor and a character can never collide on ID). The engine does not validate what an entity's narrative properties contain — that was never a source of the failures being fixed here, and a schema for it would only constrain the DM's prose for no engine benefit.

   The shared keyspace has to be guarded from **both** sides, and getting only one of them is a live defect rather than a theoretical one. The narrative store refusing to `create` onto an ID the engine holds is the easy half. The other half is the engine refusing to *mint* onto an ID the narrative store holds: a DM that created the objective `iron-key`, followed by a scene producing an item named "Iron Key", puts two different things under one ID, and the flat render folds them into a single record — the exact two-truths defect this ADR exists to end, arriving through the one door left open. Because `rules` cannot import `narrative` (the dependency runs the other way, deliberately, so the ownership boundary holds), the engine takes a `World.AlsoTaken func(string) bool` hook, set once at session construction, and consults it from `HasEntity`. One hook closes minting, `create`, and every future ID check at once.
4. Mutation stays split into two lanes, and the split is now structural rather than a matter of which tool the DM happens to call:
   - **Engine-owned concepts** — identity, existence, position, containment, ownership, inventory, equipment, health, combat, time, movement — are mutated only by the existing typed tools (`move_item`, `move_character`, `apply_damage`, `add_coins`, `create_character`, `create_location`, ...). These compute — dice, wound tiers, conservation — and a generic patch cannot.
   - **Narrative concepts** — emotion, opinion, memory, rumor, secret, relationship, story metadata — are mutated only by a new `world_update` tool call, carrying a JSON operations list, never free text.
   A draft of this design let `world_update` write `location` directly and mint whole characters with an ad-hoc `hp`. Both were caught and rejected before landing: exactly the engine-owned overlap ADR 002 already paid for once (its own recorded incident: a session lost a parchment because the DM read its own ledger entry back as proof the item was already recorded).
5. `world_update` operations are `Operation{Op, Entity, Properties}`, JSON in the tool call arguments — never text to parse, matching every other tool in tools.go. Three ops: `create`, `set`, `delete`. `create` and `set` require `Properties`; `delete` forbids it. `create` and `delete` only ever target narrative-only entities — never a Character/Item/Location, which are always minted by their own typed tool so the rules library computes their defaults, rather than the model inventing a number with no relationship to the wound/penalty system. `set` merges `Properties` into the target entity's `narrative` map — the same field-merge semantics the ledger used, JSON-native now, namespaced under `narrative` instead of a pipe-separated line.
6. `narrative` is the only part of an entity `world_update` may address — structurally, not by convention: the operation has no path syntax that can reach a top-level field. This alone stops an accidental overwrite of `location`/`hp`/etc., but not a synonym growing *inside* `narrative` (`narrative.location`, `narrative.current_room`) that the DM later reads back as authoritative. So a `Properties` key colliding with a reserved engine-concept name (`location`, `hp`, `wounds`, `inventory`, `equipment`, `coins`, `skills`, `attributes`, `gifts`, `faults`, `scale`, `species`, `cannot-act`, `penalty` — the existing `engineOwned` set) is rejected inside `narrative` too, with a note, exactly as the ledger rejects it today. Structural containment and the denylist each stop a failure the other doesn't; neither alone was judged sufficient.
7. The `ledger` package is retired. What it did — per-entity field-merge of DM-authored facts, `@tN` turn-stamping, `engineOwned` rejection — becomes the `narrative` map on each entity in the one flat rendering, keyed to the same ID as the engine entity where one exists, and standing alone (`id`, `type`, `narrative` — no engine fields) for a purely narrative construct. The three-section block (ROSTER/LOCATIONS/WORLD) collapses into the one `entities:` map; TIMELINE is unaffected in concept.
8. The archive stops recording prose as its unit. `archive.Turn.Events` becomes `[]Event{Tool, Entities, Headline}` in place of headline strings; `Turn.Update` (joined raw update text) is dropped, folded into `Events` for `world_update` calls. `Entities` on an event costs nothing new to collect: a `world_update` operation already names its `Entity`, and a typed tool call's entities come from whichever ID-bearing arguments the existing dispatch in `executeAction` already parsed (`actor_id`, `item`, `from_character`, `to_character`, ...) — no new parsing layer, just keeping IDs already in hand. A turn's own entity set is not stored as a field; it is derived by unioning its `Events`' `Entities`, the same one-fact-one-home rule the rest of this design turns on.
9. `archive.Query` gains an `Entity` field, matched exactly against a turn's derived entity set. "Has the player met this merchant" becomes an exact lookup on `merchant`'s ID rather than a hope that the word appears in the prose. Keyword search stays as a second path, for questions not tied to one entity ("what did anyone say about ghosts").
10. Deliberately not built: role-tagged event participants (`EntityRef{ID, Role}` — actor vs. object vs. recipient) for queries like "every turn X was the actor." Nothing in this design or in play needed it, and `Event`'s shape extends to carry roles later without touching anything upstream. Also not built: storing a typed tool call's full raw arguments in the archive — `Headline` plus `Entities` answers every recall case that came up; nothing has asked for the raw JSON back.

Consequences
- `rules/state.go`, `rules/location.go`, `rules/equipment.go`, and the item-related tool schemas in tools.go all change to carry and key on item IDs; `rules/location_test.go`, `tools_inventory_test.go` and neighboring tests change with them.
- `ledger/` and its tests are deleted outright. `engine_state.go`'s ROSTER/LOCATIONS/WORLD split collapses into one renderer over the flat entity map; TIMELINE's renderer is otherwise unaffected.
- dm.md loses its pipe-notation teaching (`k:v`, `!token`, `entity|GONE`) and gains the three-op vocabulary and the reserved-name list. The ROSTER/WORLD ownership framing ("these facts are the engine's, you do not write them") is replaced by the structural fact that `world_update` cannot reach those fields at all, backed by the denylist as a second line of defense should the framing itself ever be misread.
- `archive.Turn`'s shape changes; the context dump and any recall rendering built against `Turn.Update`/`Events` as strings are rewritten against the new `Event` struct.
- The `recall` tool's schema and description (tools.go:202) gain an `entity` parameter alongside `query`/`turn`/`to`.
- docs/engine-held-context-spec.md still describes the pipe-grammar ledger and the three-section block; it is now stale in those sections and due a pass when the implementation lands, but is not rewritten by this ADR.
- Save/load remains out of scope, as ADR 002 left it. The flat map plus the archive are no less serialisable for being restructured — if anything, ID-stable entities and structured events are the easier thing to write out.

Rationale
- One fact, one home, applied one layer further: the entity map replaces three sections that could each hold a claim about the same thing; the narrative namespace replaces a denylist as the *only* guard against a fact growing a second name; a stable item ID replaces a key whose meaning changed the moment the item did the one thing items do — move.
- The two-lane mutation split restates ADR 001's argument once more: dice math is not LLM math. This extends it to say patch math isn't either — anything the rules library must compute (a wound tier, a conserved count) stays behind a call built to compute it, whatever the wire format of the alternative looks like.
- Structural containment and a denylist are deliberate belt-and-suspenders, not redundancy: a boundary held up only by naming a field degrades one invented synonym at a time, since the denylist can only reject what it already knows to list; a boundary held up only by a namespace still lets a synonym grow *inside* that namespace where the DM can mistake it for truth later. Each catches what the other misses.
- Entity-indexed recall was not a new capability so much as an unpaid-for one: every mutation already names its entity to make the call at all. The old substring search existed because the old ledger lines were free text with nothing reliable to index on; once identity is real and stable, indexing on it is close to free.
