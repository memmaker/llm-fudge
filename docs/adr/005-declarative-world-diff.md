ADR 005: Declarative world diff, prose as the response body, and one call per turn
Status: Accepted
Supersedes: ADR 004 §4 (the two mutation lanes and the typed-tool half of the split), §5 (the `world_update` JSON operations grammar), §6 (structural containment of the DM's writes to the `narrative` map, and the `engineOwned` denylist that backed it), and the engine-assigned half of §1 (IDs are now model-minted and engine-validated). Leaves ADR 004 §1's flat entity map, §2 (item IDs), §3 (the kernel and the shared keyspace), §7 (the retired ledger), §8 and §9 (entity-indexed archive and recall) intact, and all of ADR 003 unchanged.

Context
- No measured failure. ADR 003 and ADR 004 each opened with a bug observed in play; this one does not, and that difference is the most important thing about it. It rests on an intuition about how autoregressive models generate — that emitting one coherent structured document is closer to the training distribution than emitting an array of semantically isolated RPC calls, and that the bookkeeping a tool-call interface demands (remember which IDs you invented, pick the right tool, order the calls, avoid duplicates, remember to call every one) is work that does nothing for the story — plus a deliberate bet that the result is materially less code. Because there is no measured failure, there is a stated way to know the bet was wrong: if entity references that resolve today start failing to resolve, or if facts the prose established stop reaching the engine at a rate worse than the tool-call interface managed, this ADR is the thing to reconsider first.
- Measured code size, which is the part of the claim that could be checked in advance: the bookkeeping half is roughly fourteen tool schemas (tools.go:131-325) and roughly four hundred lines of `executeAction` cases. A typed applier calling the same `rules` methods is around two hundred and fifty. `rules/` itself does not change.
- ADR 004 §4 justified the two mutation lanes with "These compute — dice, wound tiers, conservation — and a generic patch cannot." That argument conflates transport with computation. A declared `location: gareth` on an item still routes through `w.MoveItem`; conservation, stack splitting and ID minting all still run. The engine computes exactly as much either way. What ADR 004 was actually arguing against was an *unvalidated* patch, which is not what this is.
- ADR 004 §6's synonym-drift defence — the DM invents `current_room`, the engine ignores it, the DM later reads it back as true — was structural containment plus a denylist of known engine field names, with the note that neither alone was judged sufficient. A closed field set inverts and strengthens this: the diff *can* reach top-level fields, and every key is checked against the known fields for that entity's type. `current_room` is not a field of `character`, so it is refused with a note. The denylist caught the synonyms somebody thought to list; a closed schema catches the ones nobody did.
- Found while checking whether wounds could be declared rather than commanded: `WoundState.ApplyDamage` (rules/state.go:763) does not escalate. Past the scratch-accumulation branch it sets the level absolutely from damage points, ignoring the current level, so a Near Death character taking a one-point scratch becomes `Scratch` and a Very Hurt character taking a three-point wound becomes `Hurt`. Damage heals people. The `apply_damage` tool description asserts the opposite ("Existing wounds escalate from there"), and every `opposed_attack`/`unopposed_attack` routes through it, so this is live in combat today and not merely in the code this ADR deletes. It is fixed independently (clamp to the worse of current and new); it is recorded here because ADR 004 §4's "the engine computes wound tiers" was defending a computation that was broken.

Decision
1. **Prose is the response body.** `output_narration` is deleted. What the model writes as ordinary text is what the player reads, and the two structured blocks follow it: `<state>` carrying the world diff, and `<img>` carrying the image prompt under `--img-gen`. Nothing the player reads travels inside a tool-call argument any more. This also makes streaming the narration possible for the first time, though the client is not streaming today and this ADR does not make it so.
2. **The turn collapses to one model call on the happy path.** ADR 002's reason for splitting resolution from bookkeeping was that "what changed?", asked before the prose exists, is a prediction of text the model has not written. `<state>` written after the prose *in the same token stream* satisfies that reason more directly than a second request does: the prose is not quoted back from an earlier message, it is the tokens immediately above, in the same generation. `recordPhase`, `recordDemand` and `maxRecordRequests` are deleted. Resolution rounds are unchanged.
   Two costs are accepted. The state block is written against the block rendered before the turn's resolution calls rather than a freshly rebuilt one, so an entity created mid-turn is visible only in its tool result — which is already the situation every resolution round operates in. And until the client streams, the player waits for the state block to generate before seeing any prose, where today they read while bookkeeping runs.
3. **Mutation splits by the under-determination test, not by whether rules are involved.** The question is not "would changing this value require game rules?" — by that test item movement, coin spending and character creation all involve rules, fourteen tool calls become fourteen event tags, and nothing is gained. The question is: **does the declared end state under-determine the rules outcome?**
   - It does not for position, containment, ownership, quantity, coins, traits, weapon and armor ratings, or entity creation. The engine derives the operation from the state delta and runs the same rules it runs today. These are declared in `<state>`.
   - It does for health. Scratch accumulation depends on history — a scratch on a twice-scratched character is Hurt, on a fresh one is Scratch — so the model cannot name the end state without performing the rules itself. Health is therefore not writable in the diff at all: `wounds` and `scratches` are absent from the schema, and move only through the `<damage>` and `<heal>` event tags embedded in the narration, and through the dice tools.
   Health is the only member of the event category found by this test. The vocabulary is three tags — `<damage>`, `<heal>` and `<dead>` — not a grammar. Death is the third because it was never a consequence of arithmetic even before this ADR: `ApplyDamage` stops at Near Death and killing has always been an explicit act, so the declaration needs somewhere to live and `wounds` is not a writable field.
4. **Health is unspellable in YAML, which is what disposes of the heal-versus-amnesia ambiguity.** A declared `wounds: hurt` on a Very Hurt character means either "she was treated" or "the model forgot how bad it was", and no engine check can tell those apart. Because the schema has no such field, the ambiguity cannot be expressed by accident.
5. **The model mints IDs; the engine validates them.** ADR 004 §1's engine-assigned IDs are incompatible with a block keyed by ID — writing `entities: {crooked-lantern: {...}}` *is* minting, and there is no reply to read an ID off. The engine stops being an identity generator and becomes an identity validator, enforcing: kebab-case format (`^[a-z0-9]+(-[a-z0-9]+)*$`, refused rather than coerced as `slug()` does today); uniqueness across the one shared keyspace of ADR 004 §3; and immutability — a key that already exists is an update, never a rename, and the engine never infers renames. `name` changes freely; the key never does.
   `HasEntity` and its `AlsoTaken` hook gain a third source, a set of retired IDs, so one check closes minting, creation, collision and reuse together.
   `create_character` gains a required `id` argument in the play-time tool, so that one convention covers both places an entity can be born during a game. The character-creation copy of the schema keeps deriving the id from the name: nothing is reading a block at that point, and the player character is minted before the DM exists.
6. **Semantic IDs, not opaque ones.** `merchant-alric`, not `char_a81f92`. The handle is the model's mental grip on the entity; an opaque ID reintroduces the translation layer this ADR exists to remove. The residual risk is semantic drift — `old-blacksmith` on turn 1, `harlan` on turn 10, two entities for one person — which is a schema-documentation problem, not an ID-generation problem, and the block the model reads already lists every existing ID under which the answer is written.
7. **Merge semantics are part of the schema shown to the model, not an implementation detail.** Missing fields are unchanged. Maps merge recursively; `null` removes a key. Lists replace entirely; `[]` empties. Scalars replace. Derived fields are not writable at all.
   Derived fields are excluded from merge semantics rather than given one, which removes the worst ambiguity before it can be argued about: `inventory` (derived from each item's own `location`), `here` (derived from characters' `location`), `penalty`, `cannot_act` and `scene` are refused, because the block holds authoritative facts and never cached views. This is ADR 004 §1's one-fact-one-home rule applied to writes.
   Implicit append is rejected: a list in the block would otherwise mean either "these are now the gifts" or "add this gift", and no reader can tell. If incremental list operations are ever needed they arrive as an explicit `add`/`remove` form, never inferred from merge behaviour. `null` is not overloaded onto lists, where it would ambiguously mean delete-the-field, set-to-null, empty, or remove-the-property.
8. **Nothing important is erased; things transition out of the active state.** The world state holds what currently exists in the fiction, the archive holds what existed historically. `count: 0` is the single destruction spelling for items — every item has a count, so it covers a spent quiver and a shattered artifact alike, and partial consumption (`count: 2` from five) is the same field and the same operation. It retires rather than deletes: the ID goes to the tombstone set, the entity leaves the block, and `recall` on it still resolves (ADR 004 §9). Characters are never removed — a dead character stays in the block, lootable, referenceable and still carrying whatever they carried. `delete:` remains what it was: narrative-only entities, with engine entities refused and a note explaining why.
   No generic lifecycle field (`state: destroyed`, `condition: broken`, `fuel: 0`). Nothing in the engine would branch on one, and such facts are narrative properties, which already merge, already stamp `@tN` and already render on the entity. A mechanical consequence of breakage is a rating change on a real field, not a new vocabulary.
9. **Failure is per-entity with dependency skipping, and costs at most one extra call.** Refusals gather across the whole turn and are put to the DM once, at the end: a turn can narrate more than once, and a block can arrive on a round that resolved something rather than narrating, so answering each in place would spend rounds the turn has not got. Validation runs after every new ID in the block is registered, so ordering within the block is irrelevant — references resolve against the post-creation set. An entity that fails is skipped along with anything referencing it, so a refused `merchant-alric` also refuses the item declaring `location: merchant-alric` rather than landing it nowhere. This is the rule narrative.go already follows: one wrong line should not lose the four that were right.
   The prose reaches the player before the state block is parsed, because it is valid regardless and the player should never wait on bookkeeping. Refusals produce notes naming what does exist, in the style narrative.go:255 already writes. One correction round follows, and its demand states explicitly that only a state block is wanted and the scene is closed — without that the model narrates again into a channel that is no longer open. Still failing after the correction: report it and carry on, with next turn's block as the correction, which is today's behaviour.
10. **A mid-turn tool exists if and only if a query tool depends on the state it sets.** That rule admits exactly two during play: `create_character` (an NPC must exist before `opposed_check` can name them) and `reload_weapon` (a gun must be loaded before `unopposed_attack` fires it). Everything else that straddled both sets becomes declarative: `add_weapon`/`add_armor` become an item's `weapon:`/`armor:` fields, `equip_armor` becomes `armor: {worn: true}`, `create_location` becomes an entity with `type: location`. The accepted cost is that armor donned during a turn does not protect until the next one, and that an NPC created mid-turn to be fought fights unarmed unless a block armed him on an earlier turn.
    Character creation is the exception, and keeps `add_item`, `add_weapon`, `add_armor`, `add_coins` and `equip_armor`. It runs before there is a world to declare anything against — no scene, no ids in a block, and a model that is talking to the player rather than narrating — so the setup phase is untouched by all of this, as it is by ADR 002 and 004. `remove_item` and `remove_coins` are deleted outright: nothing in creation used them, and in play they are `count: 0` and a stated total.
11. **No schema language.** CUE was evaluated and rejected: 31 transitive modules and a 22.7 MB hello-world validator against a 9.9 MB binary today, to check what a Go `Validate()` checks in a switch. `yaml.v3` is already a dependency and `Decoder.KnownFields(true)` gives closed-struct rejection — the whole of §6's replacement — for free. The checks that matter most are referential and dynamic (does `cellar` exist, is `agility` a trait *in this setting*, loaded at runtime from `settings/`), which a static schema cannot express at all and `rules` already performs. The schema is shown to the model as ordinary YAML, and validated by Go.
12. Deliberately not built: entity windowing. Items retire, but characters and locations never do, so a long session's block only grows, and the block is the prompt. TIMELINE already solved this shape of problem with `timelineWindow`/`proseWindow`; entities have no equivalent. There is no measurement saying this bites yet, and windowing is not a schema question, so it is named as a ceiling rather than designed around.

Consequences
- `tools.go` loses nine tool schemas outright and moves five more into character creation only; `callEntities` shrinks to `toolEntities` over the query tools alone, since the applier holds the IDs it used to scrape back out of JSON arguments. A new applier translates the diff into the same `rules` calls the deleted cases made.
- A second pre-existing bug surfaced while building this: `narrative.Store.remove` asked `World.HasEntity` whether an ID was the engine's, but `HasEntity` consults the narrative store itself through the `AlsoTaken` hook (ADR 004 §3), so every narrative entity read back as an engine one and `delete` could never delete anything. The store's own map is the answer, and is now what it asks.
- `main.go` loses `recordPhase`, `recordDemand`, `maxRecordRequests`, `parseNarration`, `narrationOutput` and `opHeadline`; the turn loop ends by parsing the response body instead of a tool call. `narrationDemand` survives, rewritten: the last round still has to say why its tools are gone.
- `engine_state.go` is unchanged in what it renders. The schema, the field table and the merge rules go in `system-prompts/dm.md` rather than the block: they are the same every turn, so they belong in the part of the prompt that is written once and cached, not in the part rebuilt each turn.
- The archive is unchanged. The applier derives which internal operation each declared change corresponds to and logs the same `Event{Tool, Entities, Headline}` under the same vocabulary, so entity-indexed recall keeps working as ADR 004 §8-§9 built it.
- `rules/state.go`'s `ApplyDamage` is fixed to clamp rather than overwrite, independently of everything above.
- `tools_state_test.go`, `tools_inventory_test.go`, `tools_location_test.go`, `turn_bookkeeping_test.go` and `turn_narration_test.go` are rewritten against the diff; `rules/` tests are untouched.
